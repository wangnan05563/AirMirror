# AirMirror PC mDNS 发现协议 v2.0（2026-11-22）

| 项 | 内容 |
| --- | --- |
| 关联待办 | T06109《实现 mDNS 发现协议》 |
| 关联需求 | REQ-004 自动发现与手动兜底；AC-04 同网发现 ≤3s |
| 代码范围 | `pc-client` 发现协议、发送端 UI 选择入口、CLI 现场探针 |
| 不包含 | 二维码/投屏码配对（T06110）、PC 安装包（T06111）、音频（M3） |

## 1. 实现目标

PC 发送端无需用户先查 IP：启动后立即向局域网查询 `_airmirror._tcp.local`，把接收端的名称、地址、端口和长期指纹合成一条设备记录；用户在下拉框选中即回填 IP/端口。手动输入 IP、端口、投屏码的原有路径保持不变，作为组播被防火墙或 AP 隔离阻断时的兜底。

发现只负责“找到谁”，不自动发起连接，也不改写投屏码校验流程。这样即使发现失败，用户仍能按旧方式投屏，不会因新协议把主流程锁死。

## 2. 协议口径

| 项 | 取值 |
| --- | --- |
| 服务类型 | `_airmirror._tcp.local`（Android NSD 注册为 `_airmirror._tcp.`） |
| 组播地址/端口 | `224.0.0.251:5353` |
| 查询 | 标准 DNS 查询，QDCOUNT=1，QTYPE=PTR，QCLASS=IN |
| 解析记录 | PTR → 实例名；SRV → 目标主机/端口；TXT `fp` → 长期指纹；A → IPv4 |
| 设备身份 | 优先 TXT `fp`；老接收端没有 TXT 时退回完整实例名 |
| 展示名 | 实例名去掉 `.<服务类型>` 后缀 |
| 缓存有效期 | 120s；超时未再出现即触发 `onLost` |
| 查询节奏 | `start()` 立即发一次；之后每 5s 补发；`queryNow()` 手动补发 |

解析器支持 DNS 压缩指针、UTF-8 中文标签、截断报文和未知记录类型。遇到坏报文只丢弃当前记录或当前包，不让接收线程退出；端口 5353 被占用、加入组播失败、发送失败都通过 `onError` 上报到界面日志。

## 3. 代码与线程模型

| 文件 | 职责 |
| --- | --- |
| `pc-client/src/main/kotlin/.../MdnsDiscovery.kt` | `MdnsDiscovery` 生命周期、组播收发、设备缓存；`MdnsPacket` 编解码；`MdnsDevices` 记录合成 |
| `pc-client/src/main/kotlin/.../Main.kt` | 发现下拉框、刷新按钮、手动 IP 兜底；`--discover` 现场探针 |
| `pc-client/src/test/kotlin/.../MdnsPacketTest.kt` | 不依赖真实网卡的报文构造、解析、合成、本机假接收端测试 |

`MdnsDiscovery` 在后台线程 `airmirror-mdns` 收包，UI 回调统一 `SwingUtilities.invokeLater` 回 EDT；关闭窗口时先停发送引擎再关闭发现 Socket。所有非回环、已启用且支持组播的网卡都加入组播组，避免多网卡机器只走默认网卡；没有任何网卡加入成功时再尝试 JDK 默认组播接口。

## 4. 交互与验收入口

1. 打开 PC 发送端，局域网设备下拉框显示“未发现接收端，可手动输入 IP”。
2. 接收端启动广播后，下拉框出现 `名称  IP:端口`；选中即回填 IP 和端口，投屏码仍需用户输入。
3. 点击“刷新发现”立即补发查询，不改变已选设备。
4. 现场无 GUI 时可跑 5 秒探针：

```powershell
.\gradlew.bat --offline :pc-client:run --args="--discover --seconds 5" --console=plain
```

探针输出首台设备的 `first=<毫秒>ms`，可直接对照 AC-04 的 3 秒门槛；没有接收端时输出“发现 0 台接收端”。

## 5. 验证证据

| 验证 | 结果 | 说明 |
| --- | --- | --- |
| `MdnsPacketTest` | 5/5 通过 | query 编码、PTR/SRV/TXT/A 合成、无 TXT 指纹回退、截断报文、本机假接收端 |
| `pc-client:test` 全量 | 12/12 通过 | 含原有 `PcConnectionTest`、`SenderEngineTest`、编码器与 AnnexB 测试 |
| 本机假接收端首台耗时 | 41ms，≤3000ms 断言通过 | 验证“查询→响应→解析→合成”链路时延；不等同真实 Wi‑Fi 组播时延 |
| 真实局域网 5s 探针 | 0 台 | 当前环境没有正在广播 `_airmirror._tcp` 的接收端，AC-04 现场项未闭环 |

真实局域网项不伪造通过：需要在同一路由器下启动 Android 接收端，分别记录 5GHz/2.4GHz 的首台发现耗时，并覆盖 Windows 防火墙首次放行、AP 隔离开启两组场景。该现场项登记到 T06128 全量 AC 验收。

## 6. 已知边界与风险

- **AP 隔离/访客网络**：组播被路由器阻断时发现必然为空，界面必须继续允许手动 IP；物理路由器验证放到 T06129。
- **Windows 防火墙**：首次运行可能弹窗拦截 UDP 5353；安装向导（T06111）需要预置入站规则说明。
- **端口占用**：Bonjour、其它 mDNS 服务可能已占用 5353；`reuseAddress` 已开启，仍失败时只降级为手动输入，不影响投屏。
- **多网卡/VPN**：Tailscale、虚拟网卡会稀释组播；当前遍历所有可用网卡，但不保证跨 VPN 发现。
- **IPv6**：AAAA 可解析但不参与主机选择；当前仍以 A 记录或 SRV 目标作为连接地址。
- **安全**：发现结果只是候选，不提供信任；真正的配对、PIN、Token 由 T06110/T06112 负责。
