# AirMirror 二维码配对 v2.0（2026-11-22）

| 项 | 内容 |
| --- | --- |
| 关联待办 | T06110《开发二维码配对逻辑》 |
| 关联需求 | REQ-004 二维码/投屏码配对、记忆设备；REQ-021/AC-04 首次投屏链路 |
| 代码范围 | TV 二维码载荷（既有）、PC 摄像头/截图扫码、配对授权回调、最近设备记忆与忘记 |
| 不包含 | TrustRegistry 永久信任升级（T06112）、PIN 锁定（T06114）、安装脚本（T06111） |

## 1. 结论

1. TV 端二维码继续使用既有 `airmirror://pair` 载荷，不新增第二套协议；二维码里同时带设备标识、展示名、地址、端口和 16 位一次性令牌。
2. PC 端新增“扫码配对”：优先打开摄像头连续解码；没有摄像头或驱动异常时，直接导入电视二维码截图，主流程不被硬件锁死。
3. 扫码成功后只回填地址、端口和令牌，用户仍点“开始投屏”才发起连接；不在扫码瞬间偷偷连接。
4. “记忆设备”只在接收端返回 `AUTH_RESULT.accepted` 之后写入 `%APPDATA%\AirMirror\paired-devices.tsv`；失败、拒绝、超时都不记。
5. 记忆只保存设备标识、展示名、IP、端口和最近使用时间，**不保存一次性令牌**。再次连接必须重新扫码或输入当前投屏码，避免把已消费令牌当长期密码。
6. “忘记设备”删除本地记录；如果忘记的正是当前地址，同时停止发送引擎。

## 2. TV 端二维码口径（既有能力）

| 项 | 取值 |
| --- | --- |
| Scheme | `airmirror://pair` |
| 参数 | `id` 设备标识、`n` 展示名、`h` 局域网 IPv4、`p` 端口、`t` 16 位十六进制令牌 |
| 生成 | `Pairing.qrPayload(host, port, name)` → `Qr.into(qrView, payload, QR_PIXELS)` |
| 令牌生命周期 | 与 6 位投屏码同生同灭：60 秒轮换，旧令牌 10 秒宽限，成功一次即作废 |
| 轮换刷新 | `refreshWaitingPage()` 每秒刷新码面板；载荷变化才重画二维码，避免闪烁 |
| 锁定态 | 投屏码锁定期间不生成二维码载荷，避免给出“看着能用”的令牌 |
| 授权 | `AuthGate` 接受 6 位码或 16 位令牌；令牌命中即放行当次会话，不写永久信任 |

二维码载荷的 UTF-8 中文名、保留字符转义和残缺字段拒绝由 `PairingLink` 负责，TV 与 PC 共用同一份 `protocol-core` 实现。

## 3. PC 扫码与配对

### 3.1 扫码入口

| 路径 | 行为 |
| --- | --- |
| 摄像头 | `CameraQrScanner` 打开默认摄像头，250ms 取一帧，`QrDecoder` 用 ZXing 解 QR；识别到合法载荷后立即停止取帧并回调 |
| 截图导入 | “导入二维码截图”选择 PNG/JPG，`ImageIO` 读图后走同一个解码器；适合没有摄像头、摄像头被占用或驱动异常 |
| 手动兜底 | 原有 IP、端口、投屏码输入完全保留；扫码失败不影响手动路径 |

`QrDecoder` 用 `RGBLuminanceSource + HybridBinarizer + MultiFormatReader`，只依赖 `com.google.zxing:core`，不引入 `javase` 或 OpenCV。相机取帧用 `webcam-capture`，仅负责预览和抓图，不参与协议。

### 3.2 扫码后的字段映射

| 二维码字段 | PC 行为 |
| --- | --- |
| `h` | 非空则回填接收端 IP；为空则保留当前手动 IP |
| `p` | 校验 1..65535 后回填端口 |
| `t` | 填入投屏码输入框，仅用于本次握手/AUTH；日志只写“扫码令牌”，不打印值 |
| `id` | 暂存为 `pendingPairId`；授权成功后与地址一起写入最近设备 |
| `n` | 状态栏展示“已扫码：电视名”，不直接作为可信身份 |

### 3.3 配对成功判定

`SenderEngine` 在 `PcConnection.authorize()` 返回 `accepted=true` 后触发 `onAuthorized(Session(deviceName, host, port))`。PC 界面在 EDT 上：

1. 用接收端返回的真实设备名 + 扫码 `deviceId` + 当前地址写入最近设备；
2. 重建最近设备下拉框；
3. 清空一次性令牌输入框；
4. 状态栏显示“配对成功：电视名，已加入最近设备”。

握手失败、AUTH 被拒、连接超时、用户中途停止都不会触发该回调，因此不会产生“看起来配对过”的脏记录。

## 4. 最近设备存储

| 项 | 取值 |
| --- | --- |
| 路径 | `%APPDATA%\AirMirror\paired-devices.tsv`；无 APPDATA 时退回 `~/AirMirror` |
| 格式 | 首行 `# AirMirror paired devices v1`；每行 `base64(id)|base64(name)|host|port|lastUsedAt` |
| 容量 | 最多 20 条，按最近使用时间倒序 |
| 去重 | 有设备标识按 `deviceId` 去重；手动连接无标识按 `host:port` 去重 |
| 原子写 | 先写 `.tmp`，再 `ATOMIC_MOVE` 替换；失败退回普通替换 |
| 敏感字段 | 不包含令牌、投屏码、截图或画面数据 |

“最近设备”下拉框只回填地址/端口并把令牌清空；用户必须重新扫码或输入当前 6 位码。这样即使本地文件被读取，也不能直接冒充已配对设备上线。

## 5. 错误与降级

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| 没有摄像头 | 对话框提示“没有检测到摄像头，可导入二维码截图” | 截图导入/手动输入 |
| 摄像头打不开 | 提示“摄像头不可用”，不弹系统异常 | 截图导入 |
| 图片不是二维码 | “这张图里没有识别到 AirMirror 配对二维码” | 重选图片/手动输入 |
| 二维码不是 AirMirror | `PairingLink.parse` 返回 null，整条拒绝 | 不拿残缺数据连接 |
| 二维码 host 为空 | 保留当前 IP 并提示手动填写 | 手动 IP |
| 令牌过期/已用 | 接收端拒绝，状态栏显示服务端原因 | 重新扫码或输入新码 |
| 用户取消 | 关闭对话框、停摄像头，不改任何字段 | 可重新扫码 |
| 忘记当前设备 | 删除记录并停止发送 | 保留手动输入能力 |

## 7. 风险与边界

- **webcam-capture 依赖 BridJ 原生库**：部分 Windows 驱动/安全软件可能拦截；失败一律降级到截图导入，不阻断配对。
- **令牌可见性**：扫码后令牌会短暂显示在投屏码输入框，便于用户核对；不写日志、不落盘。共享屏幕场景仍建议扫码后立即开始投屏。
- **一次性语义**：令牌成功一次即失效；PC 断线自动重连仍持旧令牌会失败，这是服务端安全口径，不在客户端缓存令牌绕过。
- **AP 隔离**：二维码带的是电视自报 IPv4；若路由器禁止互访，扫码能成功但连接会失败，需手动 IP/投屏码或关闭 AP 隔离。
- **多电视**：摄像头可能同时看到多块屏幕；当前按第一张可解码二维码处理，用户可取消后对准目标电视重扫。
